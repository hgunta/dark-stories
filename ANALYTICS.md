# Usage analytics design (DS-005)

## Status and scope

**Schema and local storage foundation; collection remains a design.** [backend/analytics.py](backend/analytics.py) implements pure Pydantic validation for schema v1; [backend/analytics_storage.py](backend/analytics_storage.py) provides an explicitly initialized local SQLite adapter. Neither is imported by gameplay handlers. No events or identifiers are generated, no database is provisioned or implicitly configured, and no collector or admin analytics access exists. This document proposes the smallest useful measurement contract for the Foundation phase in [PRODUCT.md](PRODUCT.md) and DS-005/DS-006 in [ROADMAP.md](ROADMAP.md). Defaults below require product/privacy review before collection. It does not authorize changing APIs, gameplay, infrastructure, settings, or deployments.

Verified against [backend/app.py](backend/app.py), [backend/game.py](backend/game.py), and [frontend/index.html](frontend/index.html). Architecture and deployment boundaries remain those in [ARCHITECTURE.md](ARCHITECTURE.md) and [DEPLOYMENT.md](DEPLOYMENT.md). Render settings, pricing, disk availability, hosted CI results, and production data have not been verified.

## Source findings and measurement boundaries

- Page boot calls `createRoom` automatically; Start Game and Random Premise also create rooms. A room is a game attempt, not evidence that a player deliberately engaged. Report zero-question starts separately.
- `ROOMS` and `CODE_MAP` are process-local. A room has `asked`, `hints_used`, `solved`, and confirmed fact sets, but no browser visit, durable analytics ID, activity timestamp, or separate solved/revealed outcome.
- `/api/message` rejects unknown rooms, returns game-over for ended games, and handles `/premise`, `/rules`, and `/help` before classification. Other text goes to the offline stub or AI classifier. The browser intercepts `/hint` and uses `/api/hint`; direct `/hint` to the message endpoint does not receive that special handling.
- `asked` increments only on the ordinary final response path, omitting AskYesNo and solve returns. Browser `QUESTIONS_ASKED` increments before a response and includes text commands passed to `sendText`. Neither is the canonical analytics count.
- Both automatic fact completion and the moderator's Solved label return a solution. Reveal sets the same `solved` flag and is repeatable. The share text says “I solved” after either outcome. Do not infer analytic outcome from the flag, reply text, or share UI.
- Hint exhaustion returns `No more hints.` with no increment. Direct hint requests remain possible after a game ends. Joining exists in the backend but has no active frontend controls or synchronized chat.
- API failures can propagate; client `fetch` errors are not centrally reported. A successful server response does not prove the browser received or displayed it.

## Identifiers and sessions

All proposed random IDs use UUIDv4, validated as UUIDs, without user content. They are pseudonymous, not guaranteed anonymous; do not equate them with people or use them for authentication.

| Identifier | Meaning, creation, and lifetime |
| --- | --- |
| `browser_visit_id` | Anonymous browser/session identifier, generated in browser `sessionStorage` for a tab visit. Rotate after 30 minutes without observed game action, after 24 hours maximum, or on an explicit privacy reset. No long-lived cookie/localStorage ID, fingerprint, account matching, or cross-device linking. Tab duplication may copy sessionStorage; a later implementation must handle or document that collision. |
| `game_session_id` | Server-generated analytics ID when a room is created, stable for that room's lifetime. Separate from the short gameplay `room_id` and invite code; keep any room mapping internal and do not persist those access selectors as event properties. One visit can create many games; one game may receive later actions from another visit. |
| `mystery_id` | Server-resolved ID from a successfully loaded catalog mystery, e.g. `ms-001`. Not an arbitrary client path/string. Pair with an optional public `content_revision` to distinguish later content changes. |
| `event_id` | Random ID allocated once for a canonical event, reused for persistence/delivery retries. Uniqueness enforced in storage. Never regenerated merely to retry an insert. |
| `attempt_id` | Server-generated correlation ID for each accepted question/hint processing execution, reused by its response/error event. Two distinct HTTP executions are two attempts, even if a user retries identical text. No text hashing for deduplication. |

Rotate visits at game-action boundaries; a long game can span visits. Store the initiating visit on the game-start event and the acting visit on subsequent events. Replay joins use the initiating visit, not any later acting visit. Missing/disabled visit storage means `browser_visit_id=null`, with explicit coverage counts; never fabricate it using IP or user-agent. No cross-device or returning-person metric is supported.

A **browser visit** groups temporary tab activity; a **game session** follows one created room. Reload may preserve the visit but the existing UI creates another room. Treat it as another start; an optional `start_source=page_load` helps interpretation, but cannot be established by the backend alone.

## Common event envelope and validation

Every event requires the following fields, including nullable fields where specified. Event-specific required properties are additional to this envelope. The event catalog below defines all nine names; reject unrecognized names and properties instead of persisting arbitrary payloads.

| Required field | Rule |
| --- | --- |
| `schema_version` | Integer `1`; breaking semantic changes require a new version. |
| `event_name`, `event_id` | One catalog name and valid unique UUID. |
| `environment` | Server-set `production`, `staging`, `local`, or `test`; never trusted from client input. Default product reports select production. |
| `source` | `server` or `derived`; canonical events come from trusted backend hooks or inactivity reconciliation. Client metadata never proves a solve or delivery. |
| `occurred_at`, `recorded_at` | UTC RFC3339 timestamps with milliseconds. Server records both; recorded time may be later due to retry or reconciliation. Ordering uses a per-game server sequence, not client clock or UUID order. |
| `game_session_id`, `mystery_id` | Required non-null for all events except `game_error`, where null is allowed if no valid game/catalog association exists. |
| `browser_visit_id` | UUID or null. Validate length/format and bind to the observed request; untrusted metadata, never identity or permission evidence. Derived abandonment inherits the latest observed visit or null. |
| `mode` | Server-derived `offline` or `ai` at the action; null only for an error before mode can be resolved. For abandonment use the last observed mode. Game-start mode is the default metric cohort; flag/exclude mixed-mode games from AI difficulty comparisons. |
| `game_sequence` | Increasing integer assigned transactionally for events in a game; null for unassociated errors. Prevents ambiguous simultaneous terminal ordering in the analytics ledger. |
| `properties` | Strict event-specific object below. Bound payload to 4 KiB; allow only finite numbers, bounded integers, booleans, UUIDs, enum values, and approved public revision strings. No free-text bags. |

Common optional fields: `content_revision` and `app_revision` (bounded public commit/version references). No arbitrary client timestamp is retained in v1. `occurred_at` is when the backend observed the condition, not when a human clicked; request failures before reaching the server are outside canonical question-attempt counts. Use monotonic elapsed time for optional `latency_ms` (integer 0–300000); do not subtract client clocks. Invalid analytics data must not fail or alter a game request.

### Common deduplication and ordering

Persist `event_id` uniquely and enforce semantic uniqueness below within each environment. An identical retry is a no-op; a reused key with conflicting fields is rejected/quarantined as a bounded operational counter, never silently overwritten. Associate response events with an existing same-game submitted/requested event and its attempt ID; out-of-order arrival waits for reconciliation and cannot count as an orphan response.

Delivery retries must replay the original event ID, timestamp, sequence, and payload. This prevents duplicate **analytics records**, not duplicate gameplay operations: existing APIs have no idempotency key, and a repeated HTTP call can create another room or consume another hint. Distinct actual executions remain distinct attempts; no unsafe question-text deduplication. A browser click-to-request retry correlation would need a separately reviewed contract before measuring unique human actions.

The analytics ledger admits one first terminal outcome per game (`solved` or `revealed`) using transactional uniqueness and sequence ordering. Later terminal-like requests can be recorded as interactions where specified, but cannot reclassify the first outcome. Analytics serialization must not claim to fix current gameplay concurrency races; persist ambiguous concurrent cases as excluded/flagged quality cases until explicitly resolved and tested.

Every row inherits the envelope, UTC timestamp rules, strict field allowlist, ingestion retry behavior, and per-game ordering above. Optional fields are absent unless known; no strings containing content or exceptions are permitted. Backend branch hooks and storage below are future implementation work.

## Schema-v1 implementation clarifications (DS-006A)

The standalone module exports nine typed event models, the discriminated `AnalyticsEvent` union, and `validate_event(dict_or_json)`. It uses the existing Pydantic dependency and performs no I/O. Required fields have no generated defaults: callers must explicitly supply version, IDs, times, and nullable envelope fields. Optional properties/revisions may be omitted or null (both mean unknown); standard serialization preserves required nulls and emits UUID strings and UTC timestamps. Models and nested properties are frozen and revalidated when supplied again; do not bypass validation with Pydantic's trusted `model_construct`/copy APIs when accepting untrusted data.

The following bounds resolve previously unspecified v1 details:

- IDs must be UUIDv4 objects or canonical hyphenated UUIDv4 strings; uppercase hex is accepted and serialized lowercase. Bytes, compact hex, numeric IDs, and other UUID versions are rejected. Validation does not prove uniqueness, randomness, ownership, or attribution.
- Timestamp strings require exactly three fractional digits and `Z` or `+00:00`. Aware Python datetime objects must have zero UTC offset and whole-millisecond precision. Naive, non-UTC, numeric epoch, unknown `-00:00` offsets, and finer precision are rejected rather than silently rounded. JSON serialization uses `.sssZ`. `recorded_at` cannot precede `occurred_at`; no wall clock is consulted, so historical fixtures remain deterministic.
- `game_sequence` and `hint_number` are strict integers from 1 through 2,147,483,647. Latency is a strict integer from 0 through 300,000 ms and HTTP error status from 400 through 599. Booleans, numeric strings, floats (including NaN/infinity), and coercions are rejected for integer fields. Schema version is explicitly integer `1`; inactivity is explicitly integer `1800`.
- Mystery IDs have the bounded v1 format `ms-` plus 3–8 decimal digits. Optional public revisions are 7–40 lowercase hexadecimal commit references or `v?MAJOR.MINOR.PATCH` (each number 1–4 digits) with an optional lowercase alphanumeric/dot/hyphen prerelease suffix, at most 64 characters total. No paths, prose, arbitrary metadata, or IP/user-agent fields are accepted. Syntactic validation cannot prove catalog membership or a revision's public provenance; those remain trusted server responsibilities. A changed accepted format needs an explicit compatibility/version review.
- Only `game_error` may have unknown game/mystery/mode. Game ID and sequence are either both null or both present; an associated game requires a mystery ID. A creation failure may know a valid mystery without having a game. Null mode is allowed only for `before_acceptance` errors. All nullable fields remain required, even when null.
- All events are `source=server` except `game_abandoned`, which requires `derived` and an effective time exactly 1800 seconds after `last_activity_at`. Offline question responses must be Unknown offline stubs; AI responses cannot be offline stubs, and AI fallback must be Unknown. These are local consistency checks, not proof of an actual source operation.
- The **entire serialized event**, not only properties, is capped at 4096 UTF-8 bytes. The helper also rejects raw JSON over 4096 bytes before parsing, including whitespace. Strict property/envelope allowlists and bounded fields leave normal valid v1 events well below this limit. Fields are not truncated to force acceptance.

No validator implements catalog lookups, server-derived environment trust, event uniqueness, request pairing, sequence monotonicity across records, terminal precedence, hint-count lookup, pending activity, abandonment reconciliation, consent, retention, or persistence. A syntactically valid event is not authorization to collect or publish it. Values encoded in an otherwise valid ID/revision cannot be semantically identified as sensitive by a schema; producers must use trusted identifiers and public revision references only.

The module never logs input. Rejected values are hidden in ordinary model/adapter error formatting, but Pydantic diagnostics can still contain untrusted keys/tags and structured input/context. Future consumers must not log raw payloads, validation strings, or structured errors; map failures to bounded approved operational codes instead.

Breaking field or semantic changes require a new `schema_version` and a documented reader/migration policy. V1 rejects unsupported versions; do not silently reinterpret old records or widen free-text fields. Collection and infrastructure approval remains separate from schema acceptance.

## Local SQLite storage foundation (DS-006B)

`SQLiteEventStore(database_path)` is an internal adapter using Python's built-in `sqlite3`. The caller must supply a filesystem path; there is no default path, environment lookup, connection at import/construction, or application integration. Relative paths are resolved at construction. `initialize()` explicitly creates the file and version-1 table/indexes, but does not create parent directories. SQLite URI strings and `:memory:` are rejected because each operation uses an independent connection; pytest uses isolated files under `tmp_path`. Read/insert operations require an existing initialized file and do not create a missing database.

Small interface:

- `initialize()` creates the table/indexes transactionally and is idempotent for a compatible initialized database. SQLite `user_version=1` identifies this adapter's storage format, separately from event `schema_version=1`. Unknown database versions are rejected; no migration or destructive reset is attempted. Use a dedicated file, not an unrelated application's database.
- `insert(event)` accepts only a DS-006A model and revalidates it, including models created/copied through Pydantic bypass APIs. Dicts/JSON are rejected; callers validate them first. Canonical JSON includes defaults and required nulls; semantically identical normalized representations compare equally. No raw input is logged or stored on rejection.
- `insert` returns true for a new row and false for an exact retry with the same ID and canonical payload. Changing any canonical field under an existing ID raises `EventConflictError`. A different event ID cannot reuse a semantic key, even if other fields match: reject it as a conflict rather than silently ignoring producer mistakes. Retry the original event, including its sequence/times/ID.
- `get(event_id, environment=...)` returns a revalidated model or null. `read(environment=..., game_session_id=..., event_name=..., since=..., until=..., limit=100, offset=0)` returns revalidated models. Only environment is required; the other filters are optional. No arbitrary SQL, column names, or sort strings are accepted.

### Constraints, transactions, and terminal outcomes

Event IDs are globally unique within the supplied database file, a stronger constraint than environment-scoped semantic keys. Per-game sequences are unique within `(environment, game_session_id)`. Null game/sequence errors can coexist. Semantic keys enforce one start per game, one event of each attempt-based type per game/attempt, one error per environment/attempt, and one abandonment inference per game/last-activity/rule version. All keys are generated from validated fields, never player text. These checks prevent duplicate analytics rows, not repeated actual gameplay executions.

Every insert uses `BEGIN IMMEDIATE`, checks existing IDs inside the same transaction, and commits only on success. Uniqueness constraints arbitrate competing writers across independent connections/store instances. Any exception rolls back the transaction, including trigger side effects; connections always close. The adapter uses SQLite's standard local journaling, a bounded five-second lock timeout, and no background worker or automatic retry. Lock/I/O errors propagate to the caller; a future emitter must contain them so gameplay remains fail-open. No gameplay handler currently calls storage.

A partial unique index permits only one terminal assertion per environment/game: `game_solved` or a `solution_revealed` with `establishes_outcome=true`. An exact retry is a no-op; a second assertion with another ID raises `EventConflictError` and leaves the original unchanged. A later reveal with `establishes_outcome=false` is accepted only when a stored terminal has a strictly smaller sequence. It records an interaction without adding another outcome. The adapter does not manufacture a terminal outcome or rewrite producer flags.

**Out-of-order limitation:** nonterminal events can arrive with noncontiguous/out-of-order unique sequences. Game-scoped reads sort them by sequence. Terminal competition preserves the first successfully stored assertion, not an inferred earlier business outcome: an arriving assertion with an earlier sequence still conflicts. A nonterminal reveal arriving before its terminal must be retained/retried by a future producer/reconciler. Conflicts require explicit reconciliation before reporting; this adapter does not silently resolve ambiguous outcomes or claim gameplay concurrency is fixed. No aggregate/rate API is implemented.

### Query bounds and local file behavior

Queries are parameterized, including filters, pagination, and ID lookup. Environment and event-name filters are allowlisted; IDs and times use DS-006A validation. `since` is inclusive and `until` exclusive on `occurred_at`, with a nonempty ordered range when both are supplied. A game-scoped read orders by sequence then event ID; other reads order by occurrence time then event ID. Limits are strict integers 1–1000; offsets 0–100000. Results are bounded but offset pages are not a stable snapshot under concurrent writes; no cross-page consistency guarantee is made.

Indexes cover environment/game/sequence, event name with occurrence time, occurrence time/event ID, recording time, semantic key, and the terminal constraint. Reopening a file retains committed rows on the tested local filesystem. This is **not proof of Render durability**, disk availability, network-filesystem suitability, backup integrity, or resilience to hardware failure. Render's ordinary filesystem can be ephemeral; a separately approved persistent disk/database, backup/restore plan, and staging verification are prerequisites for production use. A SQLite file does not persist gameplay dictionaries.

### Deferred protections and remaining production work

This foundation does not enforce catalog/public-revision provenance, consistent mystery identity across a game's events, existence of a start, request/response matching, nonterminal active-state rules, sequence allocation/contiguity, inactivity reconciliation/resumption, hint-count lookup, or retention cutoff/replay rejection after deletion. Schema validation and uniqueness alone do not make stored rows ready for engagement reporting: orphan responses and ambiguous sequences need a future projection/reconciliation layer. Direct database modification bypasses adapter guarantees; access must remain private. Payloads are schema-validated again on read, but full tamper detection or database authorization is not supplied.

Before production collection, implement and test approved producer hooks, mappings and request pairing, fail-open error handling, privacy/consent and deletion/suppression, retention/aggregation, reconciliation and coverage counters, admin authorization, and the approved Render durability/backup configuration. No opt-out, deletion API, scheduler, collection toggle, dashboard, or live reporting is activated by this increment. All production settings/releases still follow [DEPLOYMENT.md](DEPLOYMENT.md) and explicit human approval.

## Inactivity and canonical outcomes

Proposed default: **30 minutes of observed inactivity**, evaluated on report access and by a small in-process periodic reconciliation task while the service is running. No external scheduler/queue is initially required. A sleeping service cannot guarantee timely emission; reconcile overdue games after restart and record the original effective time separately from detection time.

Activity is a successful game start or a valid pre-terminal question/hint attempt or permitted pre-terminal help/premise/rules request, observed at server receipt. Those control commands update the activity projection without a new question event. A completed pre-terminal response/error can advance the activity time to completion. Invalid-room requests, joining/polling, post-terminal hints/reveals, catalog requests, and analytics delivery retries are not engagement refreshes. No heartbeat is proposed; someone silently reading for more than 30 minutes can be misclassified. Describe the measure as **observed inactivity**, not confirmed departure.

Use durable `last_activity_at` and pending-attempt markers. Do not infer abandonment while processing is pending, but cap the pending grace at five minutes from acceptance; a crash must not keep the game active forever. With the 30-minute window, that shorter grace normally expires first. A late observed completion/activity supersedes a stale inactivity inference; effective abandonment time is always based on the latest valid activity.

Canonical report state at a given cutoff is exactly one of: solved, revealed, active/pending, inferred abandoned, or unclassified due to missing/ambiguous data. Terminal outcomes win over prior abandonment inferences. If an abandoned game receives a valid action while its room still exists, resume it in the projection and mark prior inference superseded; leave immutable source events intact. A later inactivity period has a different last-activity dedupe key. Each game counts at most once in a report's abandonment numerator. Metrics can change as players resume; include report `as_of` time and rule version. Do not sum abandonment event rows.

A restart loses gameplay rooms, even if analytics survives. Do not claim the game was intentionally abandoned at restart: retain the observed-inactivity inference and report a restart/data-loss caveat. Requests to lost rooms are errors and do not recreate/resume the game. Opening a new game while one remains unresolved does not immediately prove abandonment. Browser-close/unload signals are unreliable and unnecessary for this rule.

## Metrics and denominators

Use distinct canonical events/projections after deduplication. Group by start cohort in UTC, environment, and start mode; show the sample size, unclassified count, missing visit-ID coverage, unknown completions, and latest `as_of`. Do not blend staging/test traffic or offline stub outcomes into production AI product/difficulty reporting. A cohort is **mature** when started at least 30 minutes before `as_of`; late actions can still revise its outcome. Rates below use mature starts unless stated otherwise; report active games alongside them rather than hiding them.

| Metric | Definition |
| --- | --- |
| Game starts | Distinct games with `game_started` in the selected start window; include automatic boot starts. Also show games with at least one submitted question (“engaged starts”). |
| Question attempts / successful responses | Count distinct submitted attempt IDs / matched answered attempt IDs for cohort games through `as_of`. Success fraction = answered ÷ submitted; include Unknown/AskYesNo/fallback as technically completed, report their categories separately. Missing responses may be failures or unknown completions, not necessarily user abandonment. |
| Average questions per game | Submitted attempts ÷ all selected starts, including zero-question games; also show answered attempts per game. For mature solved/revealed games report separate distributions, not only a combined mean. Exclude help/premise/rules controls. |
| Solve rate | Distinct mature games whose first terminal outcome is solved ÷ mature starts. Revealing is never a solve. State sample/active/unclassified counts; this is not a human-verified correctness rate. |
| Reveal rate | Distinct mature games whose first terminal outcome is revealed ÷ mature starts. Repeated reveal responses and reveals after a solve do not increase it. |
| Hint usage | Pre-terminal delivered hints per game and fraction of games with at least one; also show pre-terminal requested attempts and requested-minus-delivered (includes exhaustion/errors), not just the existing counter. |
| Abandonment rate | Distinct mature games currently inferred abandoned ÷ mature starts, using canonical projection at `as_of`. Still-active/pending, terminal, superseded inferences, and unclassified games are not abandoned. |
| Replay rate | Within non-null initiating visit IDs, fraction of eligible solved/revealed games followed by another game start in that same visit within 30 minutes after ending. One predecessor contributes at most once. Order by server timestamps/sequence tie-breaks; only games ended at least 30 minutes before `as_of` are eligible. Distinct later starts may be reloads, so this is observed replay, not proof of intent or returning users. Missing visits excluded with coverage shown. |
| Mystery-level difficulty indicators | Per mystery and content revision in production AI mode: solve/reveal/abandonment rates, median and p75 question attempts for solved games, pre-terminal hint use, and elapsed start-to-terminal time. Use at least 20 mature starts before publishing comparisons; show uncertainty/sample sizes and survivor bias. Elapsed time includes reading/idle time, not active play duration. Exclude mixed-mode/ambiguous games; authored difficulty metadata is context, not measured truth. |

Solve + reveal + inferred abandonment + active/pending + unclassified partitions a mature cohort; do not present the first three as exhaustive. Browser replay/visits are optional-coverage metrics; never report unique players from them. No numerical product targets or baseline are assumed. Ratings/issue analytics belong to later DS-007/DS-008 work, not new events in this schema.

## Privacy, access, retention, and deletion

- No raw questions by default, even hashed; no response prose, prompts, hints, solutions, private facts, fact indices, free-text errors, room access codes, credentials, or transcript copies in analytics. Only public catalog IDs, bounded outcome codes, and minimal correlation metadata are needed. Sending questions to OpenAI for gameplay is a separate data flow, not analytics permission.
- Do not collect names, emails, accounts, precise location, IP addresses, user-agent fingerprints, referrers, advertising IDs, or persistent cross-device identifiers. Do not copy request headers/bodies into event properties. Standard hosting/access logs may independently include IPs/paths; their settings and retention require separate review and cannot be promised by application event design.
- Make tracking purpose visible and provide an opt-out/privacy reset before collection is enabled; do not invent a legal consent exemption. Confirm applicable consent requirements and respect required browser privacy preferences. Disabled collection yields missing coverage, never a fallback fingerprint.
- Proposed retention: detailed events, game projections, and visit/game correlation maps for **30 days**, including deduplication keys; anonymous daily aggregates without individual IDs for **90 days**, then delete. Aggregates exclude small cells under 20 games and should not expose individual timing traces. Backups expire within 30 days under a verified provider policy. These are proposed defaults, not current settings or verified provider guarantees.
- Reject replays older than the detailed-data retention horizon so purged dedupe keys cannot recreate old counts. If an unusually long-running room outlives its retained analytics mapping, do not fabricate a new start or resurrect its old cohort: exclude unlinked later activity with an operational coverage count while gameplay continues unchanged. Reconciliation must not invent new games from old orphan events. Aggregates use repeatable cohort recomputation, not blind incremental addition on retries.
- Provide a future same-visit deletion mechanism using a separate opaque deletion capability, not the public analytics ID as authorization. Delete corresponding raw rows, mappings, and dedupe keys; rebuild affected retained aggregates while raw lineage is available. Explain that already irreversibly anonymized aggregates cannot identify a visitor and may not be individually retractable. After visit tokens expire or are lost, do not claim cross-device identification can find that data; expiry still applies.
