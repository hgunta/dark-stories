# Early-stage product strategy — Mystery Library first

**Decision (November 2026):** Pause the proposed Daily Mystery Challenge
and further production multiplayer investment. With scarce traffic,
daily cadence, streaks, leaderboards and DAU optimization are premature.
Focus on finding an enjoyable, shareable core experience and improving
mystery quality.

## Product promise

**Pick a mysterious case. Ask questions. Uncover the twist.
Challenge a friend to solve the same case.**

A 5–10 minute detective experience, usable without an account,
a daily login or a friend in the same room. Players can browse the
library, pick a difficulty, or choose a random case. Case-specific
challenge links let friends each start **independent sessions** with
the same puzzle; these are not a synchronized multiplayer room.

## Prioritized discovery loop

1. **First session:** A visitor opens a striking premise immediately,
   asks a question, and gets a logically sound reply.
2. **Satisfaction:** They reach a fair, satisfying explanation;
   incorrect hypotheses aren't marked Solved prematurely.
3. **Second case:** Suggest another case with a different twist or
   difficulty, rather than requiring a return the following day.
4. **Organic sharing:** A spoiler-free case link makes it easy to ask
   a friend "Can you solve this?"
5. **Editorial improvement:** Every user confusion or unfair answer
   informs a specific change to the case or moderator.

## Pilot: qualitative before analytics infrastructure

Recruit 10–20 volunteer testers through personal outreach.
Ask each to try 2–3 different puzzles. In a consent-based feedback
conversation or questionnaire, record only necessary observations:
whether they understood the rules, whether a verdict was unfair,
whether the ending was satisfying, and whether they voluntarily
started another case or shared a link. Avoid collecting identity,
raw private guesses or chat transcripts by default.

Illustrative *decision thresholds*, not claims or established KPIs:

| Question | Pilot signal | Possible product action |
| --- | --- | --- |
| Can newcomers start without help? | At least 8/10 can ask a first question | Simplify onboarding if fewer |
| Is the AI host trustworthy? | No severe spoiler or premature-solve defect in a manually checked case set | Fix moderator before expansion |
| Is the ending worth it? | Median enjoyment at least 4/5 | Rewrite weak twists rather than add more |
| Do players want another? | At least 4/10 voluntarily start a second case | Improve discovery, difficulty and quality |
| Does sharing feel natural? | At least a few testers voluntarily share a case | Refine the one-case challenge link |

The sample is small and anecdotal, so use it to identify problems and
choose a next experiment, not to claim statistical significance.

## Near-term backlog

**A. Curate the 12-case library.** Use the private offline Review Desk,
review all cases for fairness, and test representative expected
Yes/No/Unknown and valid/invalid solutions against live AI on a controlled
test budget. Approve, revise, or drop cases individually.

**B. Improve first-play UX.** Highlight a compelling case, expose
difficulty and tags, offer Random Case, and make clear how to ask
yes/no questions and submit a solution.

**C. Pilot and learn.** Recruit a few real players; summarize thematic
feedback manually without activating production analytics.
Run focused revisions and only then decide whether to expand to
20–30 puzzles or add deeper progression.

**D. Later (conditional):** Add optional collections, a better
case-rating mechanism, and eventually lightweight achievements or
retention features if repeat behavior emerges. Fully synchronized
multiplayer and AI mystery generation remain optional bets.

## Release and privacy boundaries

The review HTML generated by `tools/build_mystery_review.py` contains
solutions and private facts: **do not deploy, publish, or link it from
the public app**. Keep it on the owner's local computer; exported review
notes are also private until deliberately shared.

Existing application state is process-local. Existing URLs are public,
and solution guesses entered as ordinary chat questions are visible
in shared rooms. No new tracking, hosted dashboard, accounts,
OpenAI credentials, Render settings or production deployment is
authorized by this strategy.
